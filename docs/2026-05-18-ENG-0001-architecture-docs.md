# Architecture & Docs Research: Evennia Custom Game Creation and Typeclass Architecture

## Summary

Evennia enforces a strict separation between its core engine logic and custom game implementations. Developers do not modify the core engine codebase to create a game. Instead, custom game environments are generated by duplicating the `evennia/game_template` directory. The architecture is defined by a "Typeclass" system—an ORM abstraction layer where in-game entities (Characters, Rooms, Objects) are represented by Python classes that inherit from base classes provided by the engine. Furthermore, the system utilizes a Dual-Process architecture, physically separating the network connection handler (Portal) from the game state logic (Server), ensuring connection persistence during reloads.

## Detailed Findings

### CLI Orchestration & Process Management

* Command-line tools located in `bin/unix/evennia` (and wrapped via `evennia_launcher.py`) manage the instantiation and lifecycle of the game server.
* **Documentation vs. Implementation Alignment**: External documentation accurately describes the underlying implementation of process state mutations. The CLI natively handles starting, stopping, and hot-reloading the isolated server components without dropping socket connections.

#### Function Trace Table

| Method | Location | Parameters | Return Type | Verified Behavior |
| --- | --- | --- | --- | --- |
| `evennia start` | CLI | `[--log/-l]` | `void` | Daemonizes Portal and Server processes; initializes PIDs. |
| `evennia stop` | CLI | None | `void` | Sends termination signals to Portal/Server; closes logs. |
| `evennia reload` | CLI | None | `void` | Warm reboots Server component only; re-imports Python modules. |
| `evennia reset` | CLI | None | `void` | Cold reboots Server component; purges non-persistent scripts. |

#### Data Flow Analysis

* **Variable**: `Server Process State`
* **Created**: `evennia start`
* **Modified**: `evennia reload` (re-imports disk modules, fires `at_server_reload()` hooks)
* **Used**: Manages all game logic independent of the Portal process.

#### Semantic Properties & Evidence

* **Property**: Dual-Process Connection Persistence.
* **Evidence**: `evennia reload` documentation explicitly states it "forces the system to fire `at_server_reload()` hooks on all active memory objects... while the Portal remains active."

### Typeclass Boilerplate & Inheritance (game_template)

* Custom game logic resides entirely within the duplicated template folder (e.g., `game_template/typeclasses/characters.py`).
* **Documentation vs. Implementation Alignment**: The implementation perfectly aligns with the documented API contract. The documentation states "Database entities are mapped to Python classes." The implementation in `game_template/typeclasses/characters.py` provides empty boilerplate classes (`pass`) that explicitly inherit from Evennia's Flat API (`evennia.objects.objects.DefaultCharacter`).

#### Function Trace Table

| Method | Location | Parameters | Return Type | Verified Behavior |
| --- | --- | --- | --- | --- |
| `Character` (Class) | `game_template/typeclasses/characters.py` | N/A | `Object` | Implements `pass`. Acts as the default character type via inheritance from `DefaultCharacter`. |
| `ObjectParent` (Mixin) | `game_template/typeclasses/objects.py` | N/A | `Mixin` | Implements `pass`. Centralized mixin for overriding features across all spatial entities. |
| `Object` (Class) | `game_template/typeclasses/objects.py` | N/A | `Object` | Implements `pass`. Inherits from `ObjectParent` and `DefaultObject`. |

#### Data Flow Analysis

* **Variable**: `evennia.__init__.py` (Flat API)
* **Created**: Core Engine Initialization
* **Modified**: NEVER MODIFIED (Imported only)
* **Used**: `game_template/typeclasses/*.py` to map custom entities to database schemas.

#### Semantic Properties & Evidence

* **Property**: Core system immutability regarding custom entity creation.
* **Evidence**: `characters.py` and `objects.py` in the `game_template` are intentionally blank (using `pass`), relying completely on absolute/relative import statements (e.g., `from evennia import DefaultObject`).

### Alternative Hypothesis Check

* **Considered**: Custom Evennia games are created by directly modifying the core engine files rather than utilizing the `game_template` and Typeclass inheritance architecture.
* **Refuted by**:
1. Documentation explicitly defining the "Dual-Process Architecture" and the "Typeclass System" which maps entities for extension, not modification.
2. Code evidence from `game_template/typeclasses/characters.py` consisting entirely of `pass` statements inheriting from `DefaultCharacter`. This isolates custom game logic completely from the underlying `evennia/objects/models.py` schema generation.



## Architecture Documentation

Evennia is engineered around a non-destructive extension paradigm. The system orchestrates game environments via the `game_template` structure, providing isolated directories (`commands`, `server`, `typeclasses`, `world`) that sit on top of the Evennia package. Data persistence and entity logic are managed through the Typeclass ORM pattern, allowing developers to inject custom behavior via class inheritance (`Character(DefaultCharacter)`) rather than altering base files. The runtime environment is managed via a strict Dual-Process paradigm invoked by the `evennia` CLI, isolating the persistent networking layer (Portal) from the mutable game logic layer (Server).
