# Blackout needs a skeleton before gear

Shipped games choose one technique for each slot: a rigid model on a bone, a skinned part that replaces a body region, or a recolor. The server sends each observer **a small public record for each slot, on first sight and on a change only**. Blackout has that server half in reach, because each of the nine callers of `equip`, `unequip`, and `remove` ends in `EquipmentHandler._publish`. The client half does not exist: no animation plays, the player model has no rig (inference), and **one weapon of 21 has its own model**. The riskiest assumption is the runtime path in Godot 4.7: no tutorial binds a skinned part of one `.glb` to the skeleton of another. Thus the work starts with a skeleton and a spike, and two license questions (Quaternius and Synty) and eleven decisions for Nick stay open.

## Shipped games choose one technique for each slot

The research found eight techniques in shipped games, and no game in it uses one technique alone. World of Warcraft (WoW) shows the mix. Its player model holds mesh pieces named geosets that the client shows or hides, and an item display row names up to eight body textures ([wowdev.wiki ItemDisplayInfo](https://wowdev.wiki/DB/ItemDisplayInfo)). Helms, shoulders, and weapons are separate models on attachment points, and each point stores a bone and a position ([wowdev.wiki M2](https://wowdev.wiki/M2)). Two players wrote in 09/2024 that most armor sets have up to four attached models, and that each other part is a texture ([Blizzard forum](https://eu.forums.blizzard.com/en/wow/t/armor-fitting-tool-idea/534704)). That source is a forum post, not a developer document.

Unreal Engine names the cost of each choice for skinned parts. Its Leader Pose method has the lowest setup cost and a high cost on the render thread, because each part stays a separate mesh. Its Skeletal Mesh Merge method has a high setup cost and a low cost on the render thread, and it loses morph targets ([Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-modular-characters-in-unreal-engine)). Epic calls Leader Pose a good start for a first modular character. The notes took that last point from a search snippet.

### Old School RuneScape replaces body parts and recolors tiers

RuneScape 2 (RS2) and Old School RuneScape (OSRS) show the model that fits a low-poly game best. The findings are from the LostCityRS reconstruction of the 2004 client at branch `274` and from RuneLite, not from a Jagex document. A player is **12 appearance slots and 5 color indexes**. Each slot holds nothing, a body part named an identity kit, or an item ([Client-TS ClientPlayer.ts](https://github.com/LostCityRS/Client-TS/blob/274/src/dash3d/ClientPlayer.ts)). An item replaces the kit in its slot, so no skin exists below the gear.

An item also blanks up to two more slots through `wearpos2` and `wearpos3` ([Engine-TS Player.ts](https://github.com/LostCityRS/Engine-TS/blob/274/src/engine/entity/Player.ts)). The rune platebody takes the torso slot, blanks the arms slot, and carries its own arm model. The seven platebody items from bronze to rune name the same two models, and each item has its own recolor pairs ([Content platebodies.obj](https://github.com/LostCityRS/Content/blob/274/scripts/skill_combat/configs/melee/platebodies.obj)). The rune full helm blanks the hair and the beard ([Content fullhelms.obj](https://github.com/LostCityRS/Content/blob/274/scripts/skill_combat/configs/melee/fullhelms.obj)). A two-handed sword is the right-hand slot plus a blanked left-hand slot, so the grip is data ([Content 2hswords.obj](https://github.com/LostCityRS/Content/blob/274/scripts/skill_combat/configs/melee/2hswords.obj)).

The client merges up to 12 part models into one model and keeps the result in a cache of 200 entries. A hash of the appearance is the key ([Client-TS ClientPlayer.ts](https://github.com/LostCityRS/Client-TS/blob/274/src/dash3d/ClientPlayer.ts)). The 2004 client has no bone hierarchy: each vertex has one label, and an animation moves the labels ([Client-TS Model.ts](https://github.com/LostCityRS/Client-TS/blob/274/src/dash3d/Model.ts)). A modern engine gets the same result with rigid skin, where each vertex has full weight on one bone (inference). The appearance block holds no sheath field, so a weapon shows at all times ([RSMod PlayerUpdateBlockSegment.kt](https://github.com/Tomm0017/rsmod/blob/master/game/src/main/kotlin/gg/rsmod/game/sync/segment/PlayerUpdateBlockSegment.kt)).

### A hide list and fixed seams stop clipping

The shipped answer to clipping is to hide or delete the skin below gear. No game in the research solves it with collision or cloth. Three rules cover each case that the research found: fixed seams, a hide list on the item, and one fixed slot order (inference). The Torchlight 2 art guide requires exact seams at the neck, the forearm, and the calf, so that any two pieces meet ([Runic Games armor set guidelines](https://docs.runicgames.com/wiki/Armorset_Guidelines.html)). WoW settles a conflict between two items with a fixed order, in which gloves outrank the chest ([wowdev.wiki ItemDisplayInfo](https://wowdev.wiki/DB/ItemDisplayInfo)). Its helm rule is a table of head groups to hide, not a mesh test ([wowdev.wiki HelmetGeosetVisData](https://wowdev.wiki/DB/HelmetGeosetVisData)).

The table below is the judgment of the researcher for a solo developer with a low-poly style. It is not a statement of a source.

| Technique | Art cost for each item | Runtime cost | Fit for Blackout |
|---|---|---|---|
| Rigid attachment to a bone | Low: one mesh and one offset | One draw for each item | High for weapons, shields, hats, packs |
| Skinned part on the shared skeleton | Medium: weights for each item | One draw for each part | High for torso, arms, legs |
| Part replacement (the OSRS model) | Medium: the item is the body part | Same as a skinned part | High: no skin stays below the item |
| Geosets in one body file | High: each variant lives in the body file | Low | Low |
| Texture layers on the body | Low for each item, high for the first setup | One texture bake on each change | Low: each part needs one shared UV layout |
| Recolor of one mesh | Almost none | None | High: it multiplies each mesh |
| Mesh merge | None | Fewest draws, one bake for each look | Optional, after a measurement |
| Morph targets for body types | High | More vertex work | Low |

The advice for a small team agrees on four points, and most of it is from forum posts. Use one skeleton, and never change it. Group gear by slot, and hide what a slot covers. Attach rigid items to bones. Do not start a mesh merge or a texture bake before a measurement shows a need. One Unity instructor reports about a month of setup for one pack and months of script work ([GameDev.tv](https://community.gamedev.tv/t/equipping-armor/235633)).

## The server sends one small record, only on a change

Shipped games keep apart what the owner holds and what an observer sees. WoW 3.3.5 gives each player 19 public slot pairs, and the server writes the item template ID there, not the item instance ([TrinityCore UpdateFields.h](https://github.com/TrinityCore/TrinityCore/blob/3.3.5/src/server/game/Entities/Object/Updates/UpdateFields.h), [TrinityCore Player.cpp](https://github.com/TrinityCore/TrinityCore/blob/3.3.5/src/server/game/Entities/Player/Player.cpp)). The Lyra sample of Unreal Engine replicates the inventory to the owner only and the equipment to each client ([Epic: Lyra Inventory and Equipment](https://dev.epicgames.com/documentation/en-us/unreal-engine/lyra-inventory-and-equipment-in-unreal-engine)). Veloren syncs the full inventory of each entity, and its source carries a note to sync the minimum ([Veloren synced_components.rs](https://gitlab.com/veloren/veloren/-/blob/master/common/net/src/synced_components.rs)). A separate public record thus also protects private data (inference).

The update rule is the same in each source: the look is an event, not a part of the movement stream. RSMod writes the appearance block when a player is new to an observer, or when the block changed ([RSMod PlayerUpdateBlockSegment.kt](https://github.com/Tomm0017/rsmod/blob/master/game/src/main/kotlin/gg/rsmod/game/sync/segment/PlayerUpdateBlockSegment.kt)). Apollo keeps a version ticket for each player, and it skips the block when the observer already holds that version. It also adds at most 20 new players to one client in one cycle ([Apollo PlayerSynchronizationTask.java](https://github.com/apollo-rsps/apollo/blob/kotlin-experiments/game/src/main/java/org/apollo/game/sync/task/PlayerSynchronizationTask.java)). TrinityCore records a field change only when the value differs, and then it sends the changed fields one time ([TrinityCore Object.cpp](https://github.com/TrinityCore/TrinityCore/blob/3.3.5/src/server/game/Entities/Object/Object.cpp)).

The record is small. The block of RS2 revision 317 is **at most 56 bytes**, and the WoW 3.3.5 slot data is 152 bytes with each slot full. Both numbers are arithmetic from the field lists, not statements of a source. For JSON, the research found no measured comparison of payload shapes. Its estimate for a map of 8 slots is 220 to 300 bytes, and nobody measured it. A map from slot name to asset key tolerates a new slot, because an old client ignores a key that it does not know (inference).

The server resolves what shows before the write. RSMod writes a zero byte for the arms when the chest item covers them ([RSMod PlayerUpdateBlockSegment.kt](https://github.com/Tomm0017/rsmod/blob/master/game/src/main/kotlin/gg/rsmod/game/sync/segment/PlayerUpdateBlockSegment.kt)). A community transmog module for WoW 3.3.5 keeps a fake entry apart from the real item, and a sentinel entry hides a slot ([mod-transmog](https://github.com/azerothcore/mod-transmog/blob/master/src/Transmogrification.cpp)). Guild Wars 2 sends an item `id` and an optional `skin` for each slot ([GW2 wiki](https://wiki.guildwars2.com/wiki/API:2/characters/:id/equipment)). No design in the research gives the client a write path to the look.

Two more findings bound the design. WoW replicates the sheath state as one public byte ([TrinityCore UnitDefines.h](https://github.com/TrinityCore/TrinityCore/blob/3.3.5/src/server/game/Entities/Unit/UnitDefines.h)). The RS2 block carries seven animation IDs for stand, turn, walk, and run, so the weapon sets the stance through the look. No MUD protocol in the research sends the gear of other characters for a 3D view. Evennia sends an out-of-band message only to a client that supports it ([Evennia OOB](https://www.evennia.com/docs/latest/Concepts/OOB.html)). A telnet player thus needs the same fact as text (inference).

## Godot 4.7 has each part, but no documented recipe

Two labels bound this section. "Docs 4.7" is the stable class reference, which carried the header "Godot Engine 4.7" on 2026-10-11. "Source" is the `master` branch on that date, which is 4.8-dev. The researcher did not compare it with the 4.7 tag. Treat each source fact as true for `master` and probable for 4.3 to 4.7.

### A socket bone carries each rigid item

`BoneAttachment3D` is the standard node for a rigid item. It copies the pose of one bone into its own transform each time the skeleton emits `skeleton_updated` ([Docs 4.7](https://docs.godotengine.org/en/stable/classes/class_boneattachment3d.html), [bone_attachment_3d.cpp](https://raw.githubusercontent.com/godotengine/godot/master/scene/3d/bone_attachment_3d.cpp)). The glTF importer makes each non-joint node inside a skeleton subtree a bone ([skin_tool.cpp](https://raw.githubusercontent.com/godotengine/godot/master/modules/gltf/skin_tool.cpp)). Thus an Empty that Blender parents to the hand bone arrives as a named bone, and `bone_name` finds it (inference). A user of Godot 4.4.1 saw that result, in a thread with no reply ([Godot Forum](https://forum.godotengine.org/t/boneattachment3d-when-imported-from-a-glb-file-creates-a-new-bone-in-the-rig-with-its-name/112707)).

A socket bone moves the grip decision from code to the art (inference). One Godot 4.7 user attached a weapon with one offset for each weapon. Clips from different Mixamo downloads gave the hand bone a different basis, up to about 130 degrees apart ([Godot Forum](https://forum.godotengine.org/t/best-practice-for-attaching-weapons-items-to-a-characters-hand-across-many-animations-godot-4/141270)). One offset was thus correct in one clip and twisted in the next. The common art rule puts the grip of a weapon at the origin before export, but its sources are search snippets ([Unreal Engine answers](https://answers.unrealengine.com/questions/243098/view.html)). No source gives a standard forward axis.

Three open faults matter for a figure that the client builds at runtime. `reparent()` breaks an attachment ([#91864](https://github.com/godotengine/godot/issues/91864)). A new external skeleton on a live attachment gives a signal error ([#98204](https://github.com/godotengine/godot/issues/98204)). The bounds of a skinned mesh are wrong on some imports, and the usual repair is `custom_aabb` ([#85171](https://github.com/godotengine/godot/issues/85171)). The attachment faults that the research found for 4.3 and 4.4 closed with the 4.5 milestone.

### A skinned part binds by bone name, with one flag

A skinned mesh needs a mesh, a `Skin` with one bind for each joint, and a `skeleton` path to a `Skeleton3D`. With named binds, the skeleton resolves each bind by bone name, and the name wins over the index ([skeleton_3d.cpp](https://raw.githubusercontent.com/godotengine/godot/master/scene/3d/skeleton_3d.cpp)). Thus the bone order of the body does not matter, and only the bone names and the rest poses must agree (inference). A named bind with no such bone prints an error and uses bone 0. The manual says the same for shared animations: the bone rests must agree, not only the bone names ([Retargeting 3D Skeletons](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.html)).

Two details break a simple port. The runtime loader gives index binds unless the caller passes `GLTFDocument.IMPORT_FLAG_USE_NAMED_SKIN_BINDS` in `flags`, because the append call overwrites the state field ([gltf_document.cpp](https://raw.githubusercontent.com/godotengine/godot/master/modules/gltf/gltf_document.cpp)). Since Godot 4.6, the default of `MeshInstance3D.skeleton` is an empty path, so the code must set it ([PR #112267](https://github.com/godotengine/godot/pull/112267)). A path that reaches no skeleton detaches the mesh with no error ([mesh_instance_3d.cpp](https://raw.githubusercontent.com/godotengine/godot/master/scene/3d/mesh_instance_3d.cpp)).

**No official page and no tutorial in the research shows this bind at runtime between two `.glb` files.** Forum users report failures and return to show and hide of meshes in one file ([Godot Forum](https://forum.godotengine.org/t/gdscript-how-to-assign-a-skeleton3d-to-a-meshinstance3d/119829)). The recipe has five steps. Load with the flag, take each `MeshInstance3D` that has a `Skin`, and move it below the body skeleton. Then set `skin` and `skeleton`, and free the remainder. The recipe is from the engine source on `master`, and nobody ran it for this research.

For body regions, the method with the most Godot 4 evidence is also the simplest. The body is several meshes on one skeleton, and the client sets `visible` on each region that an item covers. One tutorial for Godot 4.4.1 puts the hidden groups in the item data ([Godot Forum tutorial](https://forum.godotengine.org/t/3d-rpg-clothing-and-inventory-system-using-godot-4-and-blender/114842)). The research found no Godot 4 source for a mask shader.

For a recolor, the safe path on this renderer is a small cache of materials with `set_surface_override_material` (inference). Instance uniforms draw black on a web export past a small node count, in an open issue for 4.5.1 ([#112674](https://github.com/godotengine/godot/issues/112674)). The repair is an open pull request with the 4.8 milestone, so Godot 4.7 does not hold it ([PR #124336](https://github.com/godotengine/godot/pull/124336)). KayKit shows the art side: one small gradient texture for the pack, so a color variant is a texture change ([KayKit Adventurers](https://kaylousberg.itch.io/kaykit-adventurers)). A palette row for each tier is an inference, and no source shows it in a shipped game.

### One clip set serves each figure

An `AnimationLibrary` is a resource, and many `AnimationPlayer` nodes can hold the same one ([AnimationMixer, Docs 4.7](https://docs.godotengine.org/en/stable/classes/class_animationmixer.html)). A track path resolves from `root_node`. One library thus drives each figure with the same path to its skeleton and the same bone names (inference). The retarget options of Godot are import settings of the editor, and the research found no runtime API for them. A file that the client loads at runtime thus keeps its bone names and its rests (inference). The model build must bake each body, each part, and each clip to one rig.

### The web export pays for each skinned surface

The Compatibility renderer skins on the GPU with transform feedback. It runs one pass for each skinned surface of each mesh instance, and only when the pose changed ([mesh_storage.cpp](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/storage/mesh_storage.cpp)). It does not batch or instance 3D draws automatically ([Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)). Each surface is thus one draw in each pass. For 100 figures of one body and ten skinned parts, the arithmetic gives **2,200 scene draws** with the depth prepass on (inference). A merge to one surface for each figure gives 200.

Godot has the API for that merge, but it has no built-in function for it. The research found no add-on that keeps the bone weights, and forum users report partial success with their own code ([Godot Forum](https://forum.godotengine.org/t/combining-meshes/55687)). A rigid item costs one draw in each pass and no skinning pass (inference). PlayCanvas gives 100 to 200 draws as a rough target for low-end mobile devices and thousands for a high-end desktop ([PlayCanvas](https://developer.playcanvas.com/user-manual/optimization/guidelines/)). That number is from another engine, and no Godot source gives one for WebGL 2.

The largest known cost is on ANGLE, the Direct3D path that browsers use on Windows. A maintainer measured 50 animated characters at **560 FPS on native OpenGL and 100 FPS on ANGLE** ([PR #124204](https://github.com/godotengine/godot/pull/124204)). The repair is an open pull request with the 4.9 milestone. An earlier report gives about 0.45 ms for each skinned body on an i7-4770K, and nobody reviewed it ([PR #124157](https://github.com/godotengine/godot/pull/124157)). No source measured Godot 4 skinning in a browser.

Animation is CPU work on the main thread. One measurement of the 4.3-dev era gives about 40 microseconds for each animated instance in each frame ([#92693](https://github.com/godotengine/godot/issues/92693)). A maintainer names `AnimationTree` as the main cost in a test of about 2,400 instances ([#101494](https://github.com/godotengine/godot/issues/101494)). The stated repairs are a bare `AnimationPlayer`, a manual `advance()` at a lower rate for far figures, and no animation for figures off the screen. Shader compiles are the last cost. This renderer has no ubershader, so the client must draw each material one time behind a load screen ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html)).

## Blackout has the server seam and almost no worn art

Each fact in this section is from a read of local files on 10/11/2026 at commit `96247fd`. No Python ran, no test ran, and the researcher opened no binary file.

### One handler method reaches each equipment change

The server has twelve equipment slots in `WieldLocation` (`blackout/items/equipment/constants.py:12-28`). `EquipmentHandler` stores a dict from slot to object in one Attribute on the player character (`blackout/items/equipment/handler.py:31-49`). Only `Character` has the handler, and an NPC has none. Each of the nine callers of `equip`, `unequip`, and `remove` ends in `_publish` (`handler.py:105-144`). `_publish` is thus the one seam for a send on a gear change (inference). Today it makes three sends, and each one reaches the sessions of the owner only.

An observer gets nothing about the gear of another character. `serialize_entity` names one asset key and one family, and each player gets the asset key `player_character` (`blackout/systems/interface/statefeed/serializers.py:809-821`, `constants.py:813-823`). A worn item has `location = None`, so a reader of room contents cannot find it (inference). The delta path compares entity ids only, so a changed row with the same id reaches no observer (inference). The PvP flag has the same problem. It sends `emit_entity_arrived` again, because the client upserts by id (`blackout/systems/gameplay/combat/pvp.py:48-93`).

Three guards meet a new field on the entity row. `test_payload_size.py` holds 1,200 entities to two thirds of a 2 MiB buffer, and it records 845,336 bytes at four actions for each row (`test_payload_size.py:56-93, 174-246`). The same file fails when a real row carries a key that the synthetic row lacks. `EntityPool._look_of` lists the fields that decide the look of a node, and its comment asks for each new field there (`godot/world/entity_pool.gd:973-985`). An item needs no new field, because its asset key is its prototype key (`serializers.py:45-89`). The files disagree on the entity radius: `constants.py:552` says 24, and `godot/README.md:272` says 10.

### The client draws static models through two code paths

`WorldView` draws the avatar of the observer, and `EntityPool` draws each other figure. Both ask `MeshResolver.resolve_entity(asset, family)` for one node (`godot/world/world_view.gd:380-409`, `entity_pool.gd:994-1006`). A search of each `.gd` and `.tscn` file found no `AnimationPlayer`, no `AnimationTree`, and no `BoneAttachment3D`. A walk is a slide of a static node, and each other figure faces one fixed way while it walks (inference). `_redraw_avatar` frees the avatar node and builds it again on each `CharState.changed`, and an HP message emits that signal (`world_view.gd:368-371`, `godot/world/char_state.gd:63-84`). A dressed avatar in the middle of a clip cannot survive that rebuild (inference).

Two loader facts shape the design. `ModelLoader._normalise` scales each model so that its longest axis is one unit, and it centres the model on the origin (`godot/world/meshes/model_loader.gd:598-610`). A sword and a body thus get the same length, and a grip at the origin does not survive (inference). `prefetch_all` asks for each manifest key behind the loading veil, and `ShaderWarmer` draws each arrival (`godot/world/meshes/mesh_resolver.gd:244-260`). The README records **13.5 s of frozen frames** for one draw of each of twenty models, on a WebGL 2 export in Chromium on 09/13/2026 (`godot/README.md:215-221`). Each new served model adds one fetch and one warm there (inference).

The player model is the weakest part. Its source is an OSRS CreatorsKit export with `license = "LicenseRef-Unconfirmed"`, and it passes the license gate by exception only (`blackout/assets/sources/osrs_player_model/source.toml:1-7`). The exception text says to replace it before a public release. The text `.gltf` of that source holds no skin and an empty animation list. The model record reads a Blender `.glb` that the researcher did not open, so "no rig" is an inference. A Quaternius base character with one skin and no animation is still in the repo, as a source that no model record uses (`blackout/assets/pipeline/budgets.py:104-119`).

The worn art is almost absent. The repo has 22 model records in six families. One weapon of 21 has its own model, `rusty_scrap_shortsword`, and its `[fix]` puts the tip up for an inventory cell (`blackout/assets/models/items/rusty_scrap_shortsword.toml:1-7`). Two bows and two arrows draw a machine gun and its clip. **None of the 18 armor items has a model**, and each one draws the `armor` family shape (`godot/world/meshes/family_shapes.gd:112-124`).

### The model build and the license gate limit the art

A model record has no field for an attach point, an offset, or hidden body regions, and the loader refuses an unknown field (`blackout/assets/pipeline/records.py:73-142`). A test holds `manifest.json` to paths only (`test_model_pipeline.py:189-200`). The build runs `prune` with `keepLeaves: false` (`blackout/assets/pipeline/build_model.mjs:378-427`). With that option, glTF Transform deletes a node that has no children and no user, and a skin that lists the node as a joint is a user ([glTF Transform prune.ts](https://github.com/donmccurdy/glTF-Transform/blob/main/packages/functions/src/prune.ts)). An empty socket node thus survives only as a joint of a skin (inference). The same step keeps `JOINTS_0` and `WEIGHTS_0`.

The export from Blender decides whether a part matches the body. "Use Rest Position Armature" exports the rest position as the joint rest pose. "Export Deformation Bones Only" exports the deform bones only ([Blender 4.5 manual](https://docs.blender.org/manual/en/4.5/addons/import_export/scene_gltf2.html)). A socket bone must thus be a deform bone, or that option must stay off (inference). The default `optimize` command of glTF Transform is unsafe for this client, because its default compression is meshopt ([glTF Transform cli.ts](https://github.com/donmccurdy/glTF-Transform/blob/main/packages/cli/src/cli.ts)). The runtime loader reads no Draco, meshopt, or quantized mesh (`blackout/assets/pipeline/glb.py:26-42`).

Godot supplies a name standard for the skeleton. `SkeletonProfileHumanoid` lists 56 bones and no weapon, back, or shield bone ([Godot docs](https://docs.godotengine.org/en/stable/classes/class_skeletonprofilehumanoid.html)). Its reference pose is a T-pose that faces +Z with no node transform ([Retargeting 3D Skeletons](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.html)). Socket bones are thus extra bones outside the profile (inference). The Blackout rule that a model faces +Z with +Y up agrees with that pose (`blackout/assets/README.md:170-173`).

The license gate permits CC0, CC-BY, art made here, and art that Nick bought (`blackout/assets/pipeline/licenses.py:66-102`). Kenney and KayKit state CC0 on each page that the researcher read ([Kenney](https://kenney.nl/support), [KayKit Adventurers](https://kaylousberg.itch.io/kaykit-adventurers)). **The Quaternius license stays unresolved.** Each pack page and the FAQ state CC0, but the license page shows a "Quaternius Asset License v1.0" of 8/28/2026 ([Quaternius License](https://quaternius.com/license.html), [Quaternius FAQ](https://quaternius.com/faq.html)). That license forbids redistribution of the assets as assets, and it permits a finished product that holds them. Its section 7 says that a change does not apply to assets that a user got under an earlier version.

The license page does not name CC0, and it does not list the packs that it covers. The safe step is to read the license file inside each download and to record that text in the source record (inference). If the new license governs a pack, that pack is not CC0 and not CC-BY, and the gate needs a new category or an exception.

**The Synty terms also stay unresolved.** The one-time purchase license forbids a share of the source files outside the team, and it says nothing about a public repository ([Synty licence](https://syntystore.com/pages/one-time-purchase-licence)). The Blackout rule keeps the files of a bought pack out of git, but git keeps the served `.glb` (`CLAUDE.md:905-910`). A served `.glb` in a public repository is a model file that any person can download. The researcher reads that as a risk under the Synty terms and states that the reading is not legal advice. The Sidekick page lists Unity and Unreal packages and no FBX or glTF file ([Synty Store](https://syntystore.com/products/sci-fi-civilians-sidekick-modular-character-pack)). No pack in the survey gives CC0 cyberpunk clothing with skin weights for a shared skeleton (inference).

## A spike first, then six phases behind one worn record

### The server names each worn item, and the client owns the body

The fact is which item shows in which slot of a character. An asset key and a `WieldLocation` value are both server facts, so the server can send them (inference from "the server names, the client draws"). The proposal is one resolver beside the equipment handler. It gives a map from slot value to asset key, and it omits each empty slot. This report calls that map the worn record, and the glossary needs a row for the noun first. The resolver is the one owner of the fact, and each reader takes the map from it.

The entity row of a player character gets the worn record as one optional field, and the server sends it only when the map is not empty. On a change, `_publish` sends the row to the area again, as the PvP flag does, and it calls `emit_avatar` for the owner. The docstring of `emit_avatar` already expects that call when appearance becomes mutable (`blackout/systems/interface/statefeed/events.py:506-554`). `room_add_player` is not coalescable, so `wear all` sends one message for each item (inference). A stale mark in the pattern of `refresh_summary` can build the row one time after the last change. `test_freshness.py` holds the proof for each write of the fact.

The size test decides between the entity row and a separate channel. Two thirds of 2 MiB less the recorded 845,336 bytes is about 550,000 bytes, or about 460 bytes for each of 1,200 rows. That number is arithmetic of this report from the two cited values. The research estimate of 220 to 300 bytes for 8 slots fits, but nobody measured it. A separate channel keeps the bytes off the largest payload, but each path that sends an entity row then needs a second send (inference). The entity row has one seam, so this report recommends it as the start.

The client owns where a slot sits on a body and how a model attaches. A table from slot value to socket bone holds that look, in the pattern of `DollLayout.ROWS`. A guard test in `test_client_constants.py` examines its keys, because a client key that names nothing is a bug. One shared builder replaces the two code paths of `WorldView` and `EntityPool`. It builds the body, asks `MeshResolver` for the art of each worn asset key, and attaches each result. The client builds each URL from the manifest, so an unknown key makes no request (inference).

Three client rules of the repo apply to the builder. The body draws at once, and each worn model sharpens in when its file arrives (`godot/README.md:210-213`). The hit flash and the hover glow write to each material below the node of a figure, so a worn child gets them (`godot/world/entity_pool.gd:517-554`). The pool measures the bottom of a node before it attaches the label, and the builder must do the same before it attaches gear (`entity_pool.gd:926-949`). A stance for each weapon class needs one more server fact, because the statefeed does not send `tool_type`. `blackout_combat` already names the attacker and the attack type to the room, so an attack clip needs no new fact (inference).

A new worn item must stay one `ItemDef` entry plus one model record. The grip of each item thus cannot live in client code. The art standard carries it: each rigid item has its grip at the origin, one fixed axis, and its real size against the body. The client then needs a second prototype of each such model that skips `_normalise`. A hide list or a second socket needs a home that the client reads with no client edit. The repository rule on a fix and a display choice does not decide that home, and question 6 asks Nick.

### The spike proves the bind, the build, and the web cost

The riskiest assumption is that Godot 4.7 binds served models to one skeleton at runtime, on the web export also. Three unknowns hide in it. The bind recipe is from the `master` source, and that source shows a change of the node tree after 4.4. The model build runs `prune` with `keepLeaves: false`, so a socket node must be a joint to survive (inference). No source measured the cost of skinned figures in a browser. The spike answers each one before any server work, and it ships nothing.

The spike needs one rigged body, one rigid sword, one skinned torso part, and one clip. KayKit Adventurers is one candidate for the body and the sword. It states CC0, and it ships rigged characters, animations, and separate weapons as glTF ([KayKit Adventurers](https://kaylousberg.itch.io/kaykit-adventurers)). The Quaternius base character is a second candidate, because its source is already in the repo with one skin. `godot/tests/smoke_model_load.gd` is the pattern for the test. The art of the spike is not a decision on the final art.

A desktop run with the `opengl3_angle` driver is the nearest stand-in for a browser on Windows (inference). That driver name is from the report in PR #124157, which nobody reviewed. The table gives each phase and the proof that ends it.

## Conclusion

The feature pays three debts that the repo already records. The placeholder player model must go before a public release, the avatar node must stop its rebuild on each HP message, and two code paths must become one builder. A plan that starts with visible gear meets each of these in the wrong order. A plan that starts with the skeleton meets them one time.

The OSRS model fits Blackout for a reason that is not about style. Blackout already permits one item for each slot, `SLOT_CONFLICTS` already clears a hand slot for a two-handed weapon, and the server already names each thing that the client draws. The unknowns are thus not in the design. They are in the art supply, in two licenses, and in a web cost that no source measured. The spike turns the web cost into numbers, and the answers from Nick turn the other two into a plan.
