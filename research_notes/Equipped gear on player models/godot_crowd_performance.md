# Godot 4 crowd performance: many animated, equipped characters in GL Compatibility (desktop and web)

Research date: 2026-10-11. Labels used in these notes:

- **[4.7 docs]** = `docs.godotengine.org/en/stable`. The page header showed "Godot Engine 4.7 documentation" on the research date.
- **[master source]** = `godotengine/godot` `master` on the research date. This is newer than the 4.7 tag. PR #124157 measured 4.7.2 stable, and PR #124204 describes the same buffer design on `master`.
- **[Compat]** = GL Compatibility renderer. **[RD]** = Forward+ and Mobile.
- **General** = advice from another engine or from a WebGL guide. It is not a Godot fact.

## 1. Skinning cost: how Godot 4 skins meshes, and what it costs

### Takeaway
[Compat] skins on the GPU with transform feedback. It runs one pass for each skinned surface of each `MeshInstance3D`, only when the pose changed, and it writes to a vertex buffer that belongs to that instance. The largest known cost is on ANGLE (the Direct3D path that browsers use on Windows): a maintainer measured 560 FPS on native GL against 100 FPS on ANGLE for 50 animated characters, and the fix is not in 4.7.

### Cited Findings
- [Compat, master source] `MeshStorage::update_mesh_instances()` does the skinning. It enables `GL_RASTERIZER_DISCARD` and runs the skeleton shader between `glBeginTransformFeedback(GL_POINTS)` and `glEndTransformFeedback()`. A skeleton-only surface takes one pass through `_compute_skeleton(mi, sk, i)`, which draws `vertex_count` points. — [mesh_storage.cpp, GLES3](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/storage/mesh_storage.cpp)
- [Compat, master source] Each skinned or blend-shaped surface of each mesh instance gets its own output buffer, `MeshInstance::Surface::vertex_buffers[0]` ("MeshInstance vertex buffer", `GL_DYNAMIC_DRAW`). A surface with blend shapes gets two more ping-pong buffers. Motion vectors add a second output buffer on demand. — [mesh_storage.cpp, GLES3](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/storage/mesh_storage.cpp)
- [Compat, master source] The engine skins again only when something changed. `mesh_instance_check_for_update()` queues an instance when `mi->dirty` is set or when `sk->version != mi->skeleton_version`. A bone write calls `_skeleton_make_dirty()`, and `_update_dirty_skeletons()` raises `skeleton->version`. A skeleton that does not move costs no skinning pass. — [mesh_storage.cpp, GLES3](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/storage/mesh_storage.cpp)
- [Compat, master source] Bone transforms live in a float array that the engine uploads to a 2D texture, `transforms_texture`, in `GL_RGBA32F`. The texture is 256 texels wide. A 3D bone takes 12 floats (3 texels). The file sets no maximum bone count, and bone indices are `GL_UNSIGNED_SHORT`. — [mesh_storage.cpp, GLES3](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/storage/mesh_storage.cpp)
- [Compat, master source] The skeleton shader reads each bone with 3 `texelFetch` calls. A vertex with 4 influences costs 12 fetches. `USE_EIGHT_WEIGHTS` raises this to 8 influences and 24 fetches. The fragment shader is empty. Transform feedback outputs are `out_vertex`, `out_normal`, and `out_tangent`. — [skeleton.glsl, GLES3](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/shaders/skeleton.glsl)
- [Compat, master source] The skeleton shader has specialization flags: `MODE_2D`, `USE_BLEND_SHAPES`, `USE_SKELETON`, `USE_NORMAL`, `USE_TANGENT`, `FINAL_PASS`, `USE_EIGHT_WEIGHTS`. — [skeleton.glsl, GLES3](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/shaders/skeleton.glsl)
- [RD, master source] Forward+ and the shared RD storage skin with a compute shader. `update_mesh_instances()` calls `compute_list_begin()`, binds `skeleton_shader.pipeline[]`, and calls `compute_list_dispatch_threads()` with the vertex count. Bones are in a storage buffer. Each instance surface gets an output buffer of the size of the surface vertex data. The dirty test is the same as in [Compat]. — [mesh_storage.cpp, RD](https://raw.githubusercontent.com/godotengine/godot/master/servers/rendering/renderer_rd/storage_rd/mesh_storage.cpp)
- [Compat on ANGLE, 4.7.x master, measured by a maintainer] PR #124204 by clayjohn, "Use _COPY buffer hints for skeleton and blend shape meshes". Scene: the Godot platformer demo changed to hold 50 animated characters. Hardware: Windows 11, Ryzen 5 9600X, RTX 4080. Results: master on native GL 560 FPS. Master on ANGLE 100 FPS. PR on native GL 560 FPS. PR on ANGLE 220 FPS. The PR says that native OpenGL mostly ignores the hint, and that on ANGLE `DYNAMIC_DRAW` puts the data in CPU-accessible memory. Status on the research date: open, approved by one reviewer, milestone 4.9. — [godotengine/godot PR #124204](https://github.com/godotengine/godot/pull/124204)
- [Compat on ANGLE, 4.7.2 stable, measured by a contributor, lower reliability] PR #124157 gave the first report of the same fault. Hardware: GTX 780, i7-4770K, Windows 11, 1360x768. Scene: one hero, 11 animated humanoid mobs, 3 NPCs (14 skinned bodies, 253 draws, 144k primitives). Render CPU for the whole frame: 1.63 ms on native GL (`opengl3`) against 9.9 to 10.2 ms on ANGLE D3D11 (`opengl3_angle`). The 11 mobs: about 0.3 ms native against 5.3 to 5.4 ms on ANGLE. The same mobs with frozen skeletons: about 0 ms on ANGLE. The same mobs drawn from static buffers: 0.1 ms. The author estimates "About 0.45 ms per re-skinned body per frame on that CPU." The maintainer closed this PR because the project does not accept AI-generated PRs, and then wrote #124204 to replace it. Treat the numbers as one unreviewed report. — [godotengine/godot PR #124157](https://github.com/godotengine/godot/pull/124157)
- [4.7 docs, all renderers] "Animation and vertex animation such as skinning and morphing can be very expensive on some platforms." The docs tell the developer to lower the polygon count of animated models, to limit the number on screen, and to lower the animation rate of far or hidden meshes. — [Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
- [4.7 docs] Renderer comparison row "Rendering cost": Compatibility has "Low base cost, but high scaling cost." Mobile has medium and medium. Forward+ has "Highest base cost, and low scaling cost." Compute shaders: "Not supported" in Compatibility. — [Overview of renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)

### Inferences
- A character built from 1 body mesh and 10 skinned gear meshes on one `Skeleton3D` costs 11 transform feedback passes for each frame in which the pose changes. A merge to one surface cuts this to 1 pass. The vertex work is the same. The saving is in the number of GL calls and buffer binds.
- The cost for each `Skeleton3D` on the render side is one texture upload (`glTexImage2D`, RGBA32F) for each frame with a bone change. One skeleton for all gear of a character is thus better than one skeleton for each gear piece.
- From clayjohn's numbers: 560 FPS is 1.8 ms and 100 FPS is 10 ms. The ANGLE penalty on 4.7-era code is thus about 8.2 ms for 50 characters, or about 0.16 ms for each character, on a Ryzen 5 9600X. With the PR it is about 2.8 ms, or about 0.055 ms for each character. Slower CPUs pay more. The #124157 report gives about 0.45 ms for each body on an i7-4770K.
- A web export on Windows most probably pays this ANGLE penalty, because PR #124157 states that browsers use ANGLE for WebGL. No source in this research measured it in a browser.
- A frozen skeleton costs about 0 ms of skinning. A lower pose update rate for far characters thus saves skinning cost and animation cost at the same time.
- The skeleton shader variants compile on first use, like every GL shader. The first skinned mesh with a new attribute set (with or without tangents, 4 or 8 weights) can cause one compile hitch. This is separate from the scene shader of the material.

### Gaps
- No source measured Godot 4 skinning in a real browser (Chrome, Firefox, Safari) with a known count of characters.
- I did not confirm whether the Mobile renderer uses the compute path. The architecture docs say Mobile "purely uses raster-based shaders", and the renderer table says compute shaders are supported on Mobile with a penalty. The two statements do not agree.
- The source read was `master`, not the 4.7 tag. PR #124204 confirms the buffer hint behavior for 4.7-era code, but I did not diff the two.
- No source gives a cost for each bone in [Compat]. The cost model above (3 texels for each bone, 12 fetches for each vertex) is from the shader, not from a benchmark.

## 2. Draw calls: what a character of N skinned gear meshes plus M rigid attachments costs

### Takeaway
[Compat] does not batch or instance 3D draws automatically. Each surface of each `MeshInstance3D` is one draw call in each pass that draws it, so a character costs about (N + M) draws in the color pass, the same again in a depth prepass, the same again for each shadow view, plus N transform feedback passes. No Godot source gives a safe draw call count for WebGL2. PlayCanvas gives "100-200 draw calls" as a rough target for low-end mobile and "thousands" for high-end desktop.

### Cited Findings
- [4.7 docs] Automatic instancing of `MeshInstance3D` nodes with the same mesh and material "is only implemented in the Forward+ renderer, not Mobile or Compatibility." — [Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
- [4.7 docs] "Godot sorts objects by Material and Shader to improve performance." The sort does not apply to transparent objects, which draw back to front. — [Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
- [4.7 docs] Depth prepass is on by default with the Forward+ and Compatibility rendering methods. — [Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
- [4.7 docs] `RENDER_TOTAL_PRIMITIVES_IN_FRAME` counts depth prepass and shadow passes, "typically" to double or triple the vertex count of the scene. — [Performance class](https://docs.godotengine.org/en/stable/classes/class_performance.html)
- [4.7 docs] Shadow render pass: "Objects will be rendered several times depending on the number of amounts of lights with shadows." — [Viewport class](https://docs.godotengine.org/en/stable/classes/class_viewport.html)
- [Compat, 4.7 docs] Lights without shadows draw in one pass. Lights with shadows use more passes. The first pass draws many unshadowed lights and at most one shadowed `DirectionalLight3D`. Each later pass draws at most one `OmniLight3D`, one `SpotLight3D`, and one `DirectionalLight3D` with shadows. "performance does not scale well with many shadow-casting lights." — [Internal rendering architecture](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html)
- [Compat, 4.7 docs] Light limits: 8 OmniLights and 8 SpotLights for each mesh ("Can be increased"), 8 DirectionalLights. — [Overview of renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- [4.7 docs] On API cost: "The communication and driver activity involved can be quite costly, especially in OpenGL, OpenGL ES and WebGL." — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [4.7 docs] The docs give one scale example: 20,000 objects with 20,000 materials render slowly, and 20,000 objects with 100 materials render much faster. The docs give no draw call threshold. — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [4.7 docs] `MultiMesh` is "a single draw primitive that can draw up to millions of objects in one go." It has no culling for each instance: visibility is "all-or-none". — [Optimization using MultiMeshes](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)
- [Compat, 4.7.2, one report] A scene of 14 skinned bodies produced 253 draws and 144k primitives. That is about 18 draws for each body across all passes. — [godotengine/godot PR #124157](https://github.com/godotengine/godot/pull/124157)
- General (PlayCanvas, WebGL): "100-200 draw calls is a rough target for low end mobile devices." "High end desktop machines on the other hand can process thousands every frame and still maintain 60fps." — [PlayCanvas optimization guidelines](https://developer.playcanvas.com/user-manual/optimization/guidelines/)
- General (WebGL): MDN gives no number and says that batching draw calls into fewer, larger draw calls generally improves performance. — [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) (read through a search summary, not a direct fetch)
- General (Unreal): Epic's example for the same problem: 50 characters with three components each make 150 draw calls without a merge and 50 with a merge. — [Working with Modular Characters, Unreal Engine](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-modular-characters-in-unreal-engine)
- [Godot 4 web, 2D, self-reported] One forum post reports 31 FPS to about 60 FPS on a mid-range Android device in a WebGL2 build. Atlases cut draw calls from 240 to 38. The scene was 2D with 260 sprites, and the gain is not isolated to draw calls. — [Godot Forum: web export stutters on mobile](https://forum.godotengine.org/t/godot-4-web-export-stutters-on-mobile-its-probably-your-art-pipeline-not-your-code-31fps-to-60fps-benchmarks-inside/143268) (read through a search summary)

### Inferences
- Draw call formula for one character in [Compat], with N skinned surfaces and M rigid surfaces, all opaque:
  - Color pass: N + M.
  - Depth prepass, when it is on: N + M more.
  - Each shadow view (each split of a directional shadow, each shadowed spot light): N + M more.
  - Each extra shadowed omni or spot light that touches the character: another additive pass.
  - Skinning: N transform feedback draws for each frame with a pose change. These do not appear as normal scene draws, but they are GL draw calls.
- Example: 100 characters with 1 body and 10 gear meshes, no shadows, depth prepass on. Scene draws: 100 x 11 x 2 = 2,200. Transform feedback draws: up to 1,100 (fewer when some gear is rigid). The same crowd after a merge to one surface for each character: 200 scene draws and 100 transform feedback draws.
- 2,200 draws is inside the PlayCanvas "thousands" range for a high-end desktop and far outside its 100 to 200 range for low-end mobile. A web build for mid-range hardware needs the merge, or a hard cap on visible gear pieces.
- A rigid attachment on a `BoneAttachment3D` costs one draw for each pass and no skinning pass. It is cheaper than a skinned gear mesh of the same size.
- Shadows from characters are the cheapest thing to remove. A blob shadow or no shadow removes one full set of draws for each shadow view.

### Gaps
- No Godot source states a safe draw call count for WebGL2 on low-end or mid-range hardware. The numbers above are from PlayCanvas and are rough.
- I did not confirm in the GLES3 scene renderer source that the depth prepass draws skinned meshes. The docs only say that the prepass is on by default.
- I did not verify the project setting that turns the depth prepass off, or its list of GPU vendors.

## 3. Mesh merging: one mesh and one skeleton for each character at runtime

### Takeaway
Godot 4 has the API to build a merged skinned mesh at runtime (`ArrayMesh.add_surface_from_arrays` with bone and weight arrays, or `SurfaceTool` with `set_bones` and `set_weights`), but it has no built-in function for it and I found no add-on that does it. Forum users report partial success with hand-written code. Unreal and Unity both treat this merge as the standard fix for modular characters, with a high one-time cost and a shared material on an atlas.

### Cited Findings
- [4.7 docs] `SurfaceTool.set_bones`: "bones must contain 4 integers." `set_weights`: "weights must contain 4 values." `set_skin_weight_count` selects `SKIN_4_WEIGHTS` or `SKIN_8_WEIGHTS`. `commit_to_arrays()` returns "the same format used by ArrayMesh.add_surface_from_arrays()". — [SurfaceTool class](https://docs.godotengine.org/en/stable/classes/class_surfacetool.html)
- [4.7 docs] `SurfaceTool.append_from(existing, surface, transform)`: "Append vertices from a given Mesh surface onto the current vertex array with specified Transform3D." The page does not say whether it keeps bones, weights, or colors. — [SurfaceTool class](https://docs.godotengine.org/en/stable/classes/class_surfacetool.html)
- [4.7 docs] `SurfaceTool`: "the attributes used before the first vertex is added determine the format of the mesh." — [SurfaceTool class](https://docs.godotengine.org/en/stable/classes/class_surfacetool.html)
- [4.7 docs] `ImporterMesh.merge_importer_meshes(importer_meshes, relative_transforms, deduplicate_surfaces = true)`: "Merges multiple ImporterMeshes into a single ImporterMesh." Surfaces with the same names and formats merge. "Surfaces with bone weights will never be deduplicated." "Blend shapes and LODs are not supported and will be discarded." — [ImporterMesh class](https://docs.godotengine.org/en/stable/classes/class_importermesh.html)
- [4.7 docs] `MeshInstance3D.bake_mesh_from_current_skeleton_pose` makes a static snapshot of the posed mesh. It is not a merge. "Mesh data needs to be retrieved from the GPU, stalling the RenderingServer in the process." "Mesh surface materials are not copied." — [MeshInstance3D class](https://docs.godotengine.org/en/stable/classes/class_meshinstance3d.html)
- [4.7 docs] On joined meshes in general: combining large meshes in real time is costly, and the docs advise to "join meshes ahead of time", by an artist or "programmatically" with an add-on. "Several objects rendered as one cannot be individually culled." — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [Godot 4.2.1, forum] One user rebuilt each surface with `SurfaceTool`, with `set_bones()` and `set_weights()`, then `index()`, `commit()`, and `mesh.skeleton = NodePath("..")`. The code "runs without error but doesn't produce any visible result." A second user merged the visible parts of a modular character "into 1 to reduce draw calls" in C# with `SurfaceGetArrays(0)` and `AddSurfaceFromArrays`. One part failed because its surface format differed (the user suspected UV2). "It's not perfect, but it served the purpose that I needed." No performance numbers. — [Godot Forum: Combining Meshes](https://forum.godotengine.org/t/combining-meshes/55687)
- [Godot 4.3, forum] The general recipe from a forum reply: `surface_get_arrays()` on each mesh, then `add_surface_from_arrays` on one `ArrayMesh`. The reply doubts that textures stay intact. — [Godot Forum: Combine multiple MeshInstance3D into 1](https://forum.godotengine.org/t/combine-multiple-meshinstance3d-into-1-meshinstance3d/88140)
- [Godot 4.4, add-on] `MeshMerger-Godot` merges child `MeshInstance3D` nodes into one `ArrayMesh`. Its README lists `Skeleton3D` and skinned meshes as a future improvement, not supported now. — [necat101/MeshMerger-Godot](https://github.com/necat101/MeshMerger-Godot) (read through a search summary)
- General (Unreal, Skeletal Mesh Merge): `FSkeletalMeshMerge` combines several skeletal meshes into one at runtime. The merged mesh "has a high initial performance cost", and the recurring render cost is lower. Epic's cost table: setup cost High, game thread cost Medium, render thread cost Low, morph targets not supported. Epic tells teams to "use one common Material" and to "decide on an atlas" for textures from the start. The main mesh must hold the full skeleton. — [Working with Modular Characters, Unreal Engine](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-modular-characters-in-unreal-engine)
- General (Unreal, Leader Pose): the cheap alternative keeps the parts separate and makes them follow one pose. Child meshes "do not use any Bone Transform Buffer and won't run any animations independently." It "does not reduce the render cost of the character on the Render Thread." — [Working with Modular Characters, Unreal Engine](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-modular-characters-in-unreal-engine)
- General (Unreal, Mutable): Mutable generates skeletal meshes, materials, and textures at runtime. It "Merges meshes to reduce draw calls" and removes hidden parts. Most of its CPU work runs on worker threads, and its operations run one at a time and are asynchronous. — [Mutable overview](https://dev.epicgames.com/documentation/unreal-engine/mutable-overview-in-unreal-engine?lang=en-US), [Mutable resource usage at runtime](https://dev.epicgames.com/documentation/unreal-engine/mutable-resource-usage-at-runtime-in-unreal-engine) (both read through a search summary, the direct fetch returned no text)
- General (Unity): a merge must keep three things aligned. `SkinnedMeshRenderer.bones` is a flat list. `Mesh.bindposes` matches it one to one: "This has to match or the skinning would be completely wrong." `Mesh.boneWeights` link each vertex to a bone index, so the code must "find the corresponding bone in the target SkinnedMeshRenderer bones array." — [Unity Discussions: Combine Skinned meshes](https://discussions.unity.com/t/combine-skinned-meshes/244559)
- General (Unity): `SkinnedMeshRenderer.BakeMesh` "Creates a snapshot of SkinnedMeshRenderer and stores it in mesh." With this call "the skinning process will always take place on the CPU". It is a pose snapshot, like the Godot bake, not a merge. — [Unity: SkinnedMeshRenderer.BakeMesh](https://docs.unity3d.com/ScriptReference/SkinnedMeshRenderer.BakeMesh.html)

### Inferences
- The merge is practical in Godot 4 when every part uses the same `Skeleton3D` and the same `Skin` (the same bone order and bind poses). Then the bone indices need no remap, and the merge is a concatenation of the vertex arrays with an index offset.
- All parts must have the same vertex format. The forum failure (one part with UV2) shows this. A fixed format for every gear model (position, normal, UV, color, bones, weights, 4 weights) removes the problem at the source.
- The merge runs only when a character changes gear, not each frame. Low-poly models (hundreds of triangles for each part) make the array work small. No source measured it in GDScript or in a web export, so the project must measure it. A spread of merges across frames (a queue, as Mutable does) avoids a hitch when many players appear at one time.
- The merge needs one shared material. Parts with different materials stay as separate surfaces and separate draws. A palette texture or vertex colors make one material possible (see question 4).
- After a merge, the client cannot cull or hide one gear piece alone. For small characters this has no cost.
- Rigid attachments (a weapon in a hand) can also go into the merged mesh, with all weights on the hand bone. This turns M extra draws into 0.

### Gaps
- I found no godot-proposals issue for runtime skinned mesh merging. Three searches of the proposals repository returned nothing on topic.
- I found no Godot 4 add-on that merges skinned meshes with weights kept.
- The docs do not say whether `SurfaceTool.append_from` keeps bones and weights. A test must confirm it. `ArrayMesh.add_surface_from_arrays` with `ARRAY_BONES` and `ARRAY_WEIGHTS` is the safer path, but I did not fetch the `ArrayMesh` class page in this research.
- The docs do not say whether `ImporterMesh.merge_importer_meshes` keeps skin data, or which Godot version added it.
- No source gives the CPU time of a merge in GDScript, on desktop or in WebAssembly.

## 4. Materials and textures: one shared material, and a color for each character

### Takeaway
One material and one palette or atlas texture remove state changes between draws and remove new shader compiles, and they are the condition for a mesh merge. For a color for each character in [Compat], vertex colors in the merged mesh are the safe method. Instance uniforms work in [Compat] since 4.4, but in 4.7 they fail past about 64 nodes on a device with the minimum uniform buffer size, and a web export shows the fault.

### Cited Findings
- [4.7 docs] "If a scene has a huge amount of objects (in the hundreds or thousands), try reusing the materials." — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [4.7 docs] "shaders are automatically reused between StandardMaterial3Ds that share the same configuration" even with different parameters. — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [4.7 docs] "In the worst case, use atlases to decrease the amount of texture changes." — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [4.7 docs] "Reading textures is an expensive operation, especially when reading from several textures in a single fragment shader." — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [Compat, 4.4 and later] PR #96819 "Implement instance uniforms in Compatibility renderer" merged on 2024-10-07 with milestone 4.4. It closed godot-proposals #6909. — [godotengine/godot PR #96819](https://github.com/godotengine/godot/pull/96819)
- [4.7 docs] Instance uniforms: "There is a practical maximum limit of 16 instance uniforms per shader." They take scalar and vector types only, no textures and no arrays. In GLSL 3.3 or lower (the Compatibility renderer), a shader cannot index a sampler array with an instance uniform. The value is set with `set_instance_shader_parameter`. — [Shading language](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/shading_language.html)
- [Compat, 4.5.1, open bug] Issue #112674: on a web export, most materials with an instance uniform color render "as if the instance color uniform was set to black". Users reproduced it in Chrome and Firefox on Linux and in Firefox on Android. — [godotengine/godot issue #112674](https://github.com/godotengine/godot/issues/112674)
- [Compat, cause and limit] PR #124336 by clayjohn (opened 2026-10-09, open, milestone 4.8) gives the cause. "OpenGL only guarantees a max UBO size of at least 16384 bytes." The same buffer holds the instance parameters. Each node that uses them takes 256 bytes (16 slots of 4 floats). At 16,384 bytes about 64 nodes can use instance data. At 65,536 bytes about 256 nodes can. The PR moves the data to a texture and reports "no measurable performance change at 1024 nodes" on a Linux integrated GPU. It fixes #114949, #112674, and #108151. — [godotengine/godot PR #124336](https://github.com/godotengine/godot/pull/124336)
- [Compat, 4.4, one device report] Instance uniforms reportedly fail on Galaxy S25 devices with Adreno 830, and work on Pixel and older Samsung devices. — [godotengine/godot PR #96819](https://github.com/godotengine/godot/pull/96819)
- [4.7 docs] The docs say of vertex colors, as an alternative to instance uniforms, that they "would require creating unique copies of the mesh for each different color, which also has a performance overhead." — [Shading language](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/shading_language.html)
- [4.7 docs] `SurfaceTool.set_color`: "The material must have BaseMaterial3D.vertex_color_use_as_albedo enabled for the vertex color to be visible." `set_custom` writes a custom channel for each vertex. — [SurfaceTool class](https://docs.godotengine.org/en/stable/classes/class_surfacetool.html)
- [4.7 docs] `INSTANCE_ID` and `INSTANCE_CUSTOM` are for `MultiMesh` instances in the vertex shader. — [Optimization using MultiMeshes](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)
- General (Unreal): for merged characters Epic tells teams to "use one common Material" and to "decide on an atlas". — [Working with Modular Characters, Unreal Engine](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-modular-characters-in-unreal-engine)

### Inferences
- [Compat] has no automatic batching of 3D draws to break. A material copy for each character does not add draw calls. It adds uniform uploads and a material count, and it does not compile a new shader when the configuration is the same.
- A crowd of 100 characters with 11 separate meshes is up to 1,100 nodes. That is far past the 64 or 256 node limit of instance uniforms in 4.7 [Compat]. Instance uniforms are thus not safe for this project on 4.7, most of all on the web. After a merge (100 nodes) the count is still above 64.
- The merged mesh already is a unique mesh for each character. The docs' objection to vertex colors (a unique mesh copy for each color) thus has no extra cost here. The merge can write the tint of each gear piece into the `COLOR` array, or shift the UVs into the correct palette row, and every character keeps the same material.
- A palette texture (one small texture, flat colors, UVs that point at texels) fits the low-poly look and makes one material possible for the body and all gear. It also removes texture binds between draws.
- `INSTANCE_CUSTOM` helps only with `MultiMesh`, thus only with a vertex animation texture crowd (question 5), not with skinned `MeshInstance3D` nodes.

### Gaps
- No source measured the gain from one shared material against many materials for skinned characters in [Compat].
- I did not confirm whether the 256-node figure applies on desktop [Compat] in 4.7. The PR also says that the default buffer size of 65536 "was basically never supported" in the Compatibility renderer.
- PR #124336 is open. The version that ships the fix is not known.

## 5. Animation cost: one AnimationPlayer or AnimationTree for each character

### Takeaway
Animation is CPU work on the main thread, and in Godot 4 it is often the first limit for a crowd. One measured figure is about 40 microseconds for each animated instance for each frame (4.3-dev era, about 4 ms for 100). `AnimationTree` costs more than a bare `AnimationPlayer`. The standard fixes are a lower update rate with `callback_mode_process = MANUAL` plus `advance()`, and a stop of animation for far or off-screen characters.

### Cited Findings
- [4.3-dev, Forward+, measured with Tracy] Issue #92693. In one user's project, `_process_animation` takes about 40 microseconds for each instance on average. "With 100 enemies, that's about 4 ms." Most of the time is in `AnimationMixer::_blend_process` (about 20 microseconds), then `_blend_calc_total_weight` (about 9 microseconds). — [godotengine/godot issue #92693](https://github.com/godotengine/godot/issues/92693)
- [4.3-dev, Forward+] Same issue: 1,024 copied characters, each with an `AnimationPlayer` and an `AnimationTree`, on a GTX 1080 and a Ryzen 5 1600. Process time rose from 16 ms to 25 to 30 ms. "Disabling animation playback returns to stable 60fps." — [godotengine/godot issue #92693](https://github.com/godotengine/godot/issues/92693)
- [4.4] PR #92838 "Optimize AnimationMixer blend process" merged on 2024-09-02 with milestone 4.4 and closed #92693. Gains for each method: blend_process about 30%, calc_total_weight about 15%, pre_process about 50%. Project result: 56 FPS (17.85 ms) to 68 FPS (14.70 ms), about +22%. Hardware not given. — [godotengine/godot PR #92838](https://github.com/godotengine/godot/pull/92838) (read through the GitHub search API, which returns the PR body)
- [4.3 and 4.4-dev7, Forward+] Issue #101494 "Animation Performance Problems" (open, confirmed). Test project: about 2,400 instances, each with an `AnimationPlayer` and an `AnimationTree`. clayjohn on an M2 MacBook Pro, in ms for each frame: 3.6: 6.2. 4.2.2: 11.75. 4.3: 13.5. 4.4-dev7: 11.0. With `AnimationMixer.active = false` on 4.4-dev7: 10.3. — [godotengine/godot issue #101494](https://github.com/godotengine/godot/issues/101494)
- [4.4-dev] Same issue, clayjohn after profiling: "So it looks like AnimationTree is the real culprit here." The time is in recursive `AnimationNode::process()` calls, in `get_node_time_info()`, in String operations, and in `make_animation_instance()`. - [4.4-dev] Same issue, the reporter's own game: about 100 AI characters at 60 FPS with animation on, and 3 to 4 times as many with animation off. Hardware: Intel i3-10105F. — [godotengine/godot issue #101494](https://github.com/godotengine/godot/issues/101494)
- [4.5 to 4.7-dev] Same issue, one user: 4.5-beta6 gives 65 FPS, 3.6.1 gives 90 FPS, and 4.7-dev3 is "much closer to 3.6.1". — [godotengine/godot issue #101494](https://github.com/godotengine/godot/issues/101494)
- [4.7] PR #117030 "Use IDs instead of hashes for TrackCache keys" merged on 2026-03-14 with milestone 4.7. [4.8] PR #118922 stops a full clear of the track cache on animation stop, which the author says caused "huge performance problems". — [godotengine/godot PR #117030](https://github.com/godotengine/godot/pull/117030), [godotengine/godot PR #118922](https://github.com/godotengine/godot/pull/118922)
- [4.x, maintainer advice] Calinou in #92693: set the process mode to Manual and step the animation less often (for example every 2 frames), "a common approach in AAA games." Stop animation playback for far nodes. The 3.x `VisibilityNotifier` had a Max Distance property that 4.x `VisibleOnScreenNotifier3D` does not have. — [godotengine/godot issue #92693](https://github.com/godotengine/godot/issues/92693)
- [4.x, maintainer] Calinou in #92693: "you'd need SceneTree multithreading to achieve reasonable performance" at that scale, and "I don't think AnimationTree is able to work in a thread-safe manner currently." — [godotengine/godot issue #92693](https://github.com/godotengine/godot/issues/92693)
- [4.7 docs] `AnimationMixer.callback_mode_process` has IDLE, PHYSICS, and MANUAL. MANUAL: "Do not process animation." Use `advance(delta)`: "Manually advance the animations by the specified time (in seconds)." `active`: "If true, the AnimationMixer will be processing." — [AnimationMixer class](https://docs.godotengine.org/en/stable/classes/class_animationmixer.html)
- [4.7 docs] The docs list these fixes for animation cost: fewer polygons, fewer animated models on screen, a lower animation rate for far or occluded meshes, and a pause of animation that the player will not notice. `VisibleOnScreenEnabler3D` and `VisibleOnScreenNotifier3D` help with this. — [Optimizing 3D performance](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html)
- [4.7 docs] `VisibleOnScreenNotifier3D` is a box region. It "uses an approximate heuristic that doesn't take walls and other occlusion into account" unless occlusion culling is in use. - [Godot 4.2, forum, one developer] "godot doesn't do skeleton 3D culling." A stop of the `AnimationPlayer` of off-screen or far units "improves performance a lot". The developer avoids `AnimationTree` because it "uses a lot of resources". - [4.7 docs, vertex animation] The docs describe a vertex shader animation with `MultiMeshInstance3D` for thousands of objects. The page carries a notice that it can be outdated for current versions. — [Animating thousands of fish with MultiMeshInstance3D](https://docs.godotengine.org/en/stable/tutorials/performance/vertex_animation/animating_thousands_of_fish.html) (read through a search summary)
- [Godot 4.5.1, add-on, vertex animation textures] `AnimatedMultimeshInstance3D` bakes animations into vertex and normal textures and plays them in a shader on a `MultiMesh`. Limits: "Animation baker doesn't support multiple surfaces." "Compatibility render mode doesn't support animation blending." "Multimesh doesn't have per instance LOD and culling." The baker stops at 8,192 vertices and 8,192 frames. Numbers: with a 3,986-vertex model, "you can feel the game struggling already at 5k+ instances". With models under 500 vertices on an RTX 2070 SUPER, "around 50k instances with a steady 100 FPS." The README does not name the renderer of these numbers. — [shadecoredev/AnimatedMultimeshInstance3D README](https://raw.githubusercontent.com/shadecoredev/AnimatedMultimeshInstance3D/main/README.md)
- [Godot 4, add-ons] Other vertex animation texture add-ons: the antzGames VAT plugin and OpenVAT for Godot (both take textures from Blender tools), and Animation Baker by lyonbeckers (bakes from an `AnimationPlayer`, with transitions for each instance). — [antzGames/Godot_Vertex_Animation_Textures_Plugin](https://github.com/antzGames/Godot_Vertex_Animation_Textures_Plugin), [antzGames/OpenVAT-for-Godot](https://github.com/antzGames/OpenVAT-for-Godot), [lyonbeckers/animation-baker](https://codeberg.org/lyonbeckers/animation-baker) (read through a search summary)

### Inferences
- A budget for 4.7: assume 20 to 40 microseconds for each `AnimationPlayer` for each update on a desktop CPU, and more in single-threaded WebAssembly. 100 characters at full rate are then 2 to 4 ms on desktop. No source measured this on the web. The project must measure it.
- For Blackout a bare `AnimationPlayer` for each character is the correct choice. The game needs only a few clips (idle, walk, run, attack), and the server sets the state. An `AnimationTree` adds cost for blend features that small characters do not show.
- An update of far characters every second or third frame through `advance()` cuts the animation cost and the skinning cost by the same factor, because a skeleton that did not change is not skinned again (question 1).
- All gear on one `Skeleton3D` needs one `AnimationPlayer` for each character. Gear with its own skeleton and its own player multiplies the cost by the number of gear pieces.
- Fewer bones cut the track count of each clip, and the mixer cost follows the track count. A low-poly humanoid of 15 to 25 bones is a reasonable target. No source gives a measured cost for each bone in Godot 4.
- Vertex animation textures on a `MultiMesh` are a poor fit for characters with changing gear. All instances share one mesh, the common add-on bakes one surface only, and a `MultiMesh` has no culling for each instance. This method fits NPC crowds with a fixed look, not equipped players.

### Gaps
- No source measured `AnimationPlayer` cost for each instance on 4.7 or in a web export.
- No Godot 4 source gives a bone count limit or a cost for each bone.
- I found no Godot 4 source for one shared skeleton that drives many characters (animation instancing) outside of the vertex animation texture add-ons.
- `VisibleOnScreenEnabler3D` properties were not on the page that I read. The class exists and inherits from the notifier.

## 6. Level of detail for equipment at a fixed camera distance

### Takeaway
Automatic mesh LOD exists in every renderer, but the editor importer makes it. The docs for runtime glTF loading do not mention LOD, so assume that a runtime-loaded `.glb` has none. For low-poly models at a fixed distance the better tool is authoring: a low triangle budget for each part, and no mesh at all for items that cover a few pixels.

### Cited Findings
- [4.7 docs] "Godot automatically generates lower-detail meshes on import for glTF, .blend, Collada, and FBX scenes." It uses meshoptimizer. The default threshold is 1 pixel (`Rendering > Mesh LOD > LOD Change > Threshold Pixels`). Selection uses a screen-space metric, so the camera FOV and the viewport resolution count. — [Mesh level of detail (LOD)](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- [4.7 docs] The LOD process "may occasionally introduce rendering issues (especially in skinned meshes)." — [Mesh level of detail (LOD)](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- [4.7 docs] Mesh LOD and occlusion culling are independent of the rendering method: occlusion culling "works the same on all rendering drivers and methods." — [Internal rendering architecture](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html)
- [4.7 docs] `GeometryInstance3D.lod_bias`: "A value of 0 will force the mesh to its lowest level of detail". `Viewport.mesh_lod_threshold`: "If set to 0.0, automatic LOD is disabled." — [GeometryInstance3D class](https://docs.godotengine.org/en/stable/classes/class_geometryinstance3d.html), [Viewport class](https://docs.godotengine.org/en/stable/classes/class_viewport.html)
- [4.7 docs] The runtime loading page shows `GLTFDocument.append_from_file` then `generate_scene`. It does not mention LOD generation, shadow meshes, or texture compression. Its introduction says: "Do not use this runtime loading approach to load resources that are part of the project, as it's less efficient". — [Runtime file loading and saving](https://docs.godotengine.org/en/stable/tutorials/io/runtime_file_loading_and_saving.html)
- [4.7 docs] `ImporterMesh.generate_lods(normal_merge_angle, normal_split_angle, bone_transform_array)`: "Generates all lods for this ImporterMesh." The class holds mesh data "during the import process". `SurfaceTool.generate_lod` is deprecated: "it does not preserve normals or UVs." — [ImporterMesh class](https://docs.godotengine.org/en/stable/classes/class_importermesh.html), [SurfaceTool class](https://docs.godotengine.org/en/stable/classes/class_surfacetool.html)
- [Godot 4.4, forum, not resolved] One user reports that `ImporterMesh.generate_lods()` creates no LODs at runtime. Another forum user says that `ImporterMesh` works only during import in the editor. — [Godot Forum: Unable to generate LODs on ImporterMesh](https://forum.godotengine.org/t/unable-to-generate-lods-on-importermesh-automatically-or-manually/111326) (read through a search summary)
- [Godot 4.0] Issue #58570 "LOD causes bones skinning errors with GLTF import" was closed as fixed for 4.0. A maintainer (fire) said in it that the LOD algorithm "doesn't handle low poly", and that automatic LOD is not needed on low-poly models. — [godotengine/godot issue #58570](https://github.com/godotengine/godot/issues/58570)
- [4.6] The 4.6 release improved LOD generation for meshes made of several separate parts: "Godot now generates LOD (level-of-detail) models that better preserve the shape of the original object". — [Godot 4.6 release page](https://godotengine.org/releases/4.6/)
- [Compat, 4.7 docs] Visibility ranges work as manual LOD. The fade modes SELF and DEPENDENCIES are "Only supported when using the Forward+ rendering method." In Mobile and Compatibility the mode "acts like" DISABLED "but with hysteresis disabled." — [GeometryInstance3D class](https://docs.godotengine.org/en/stable/classes/class_geometryinstance3d.html)
- [4.7 docs] "avoid concentration of vertices in small parts of the screen" and avoid triangles smaller than a screen pixel. — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- General (RuneScape, historical): a Jagex developer post, kept on the OSRS wiki, says: "Previously, we set a cap of five hundred polygons per model. Now, your basic human NPC still has that many, but we can use up to around 2,000-2,500 for the larger models". This is about NPC models of the old engine, not about current OSRS player kits. — [OSRS Wiki: Graphics Team, NPC Improvement Project](https://oldschool.runescape.wiki/w/Update:Graphics_Team_-_NPC_Improvement_Project) (read through a search summary)
- General (WebGL, third-party guide, weak): one guide suggests under 50,000 visible polygons for a Godot web game. It gives no device data. — [dev.to: Godot 4 for web games](https://dev.to/ziva/godot-4-fur-web-spiele-export-wasm-und-browser-performance-4315) (read through a search summary)

### Inferences
- With a fixed camera distance, every character has about the same size on screen. Automatic LOD then selects the same level for all of them, all the time. One authored detail level is enough, and LOD brings almost no gain.
- A budget in the order of the old RuneScape cap fits the look: about 500 triangles for a full human, thus about 150 to 300 for the body and 20 to 150 for each gear piece. 100 characters at 1,000 triangles each are 100,000 triangles, which is small for any GPU that runs WebGL2. The count of draws is the limit, not the count of triangles.
- Items that cover only a few pixels (a ring, an amulet) need no mesh. A color change on the body (a vertex color or a palette texel) shows them at no draw cost. After a mesh merge the triangle cost of a small item is close to nothing, so the skip matters most when the meshes stay separate.
- Because the client loads `.glb` files at runtime, it gets no LOD, no shadow mesh, and no VRAM-compressed textures from the import pipeline. The asset pipeline of the project must make the final low-poly mesh itself.

### Gaps
- No source states plainly whether `GLTFDocument.generate_scene` makes LODs at runtime. The docs are silent, and the forum reports are not resolved.
- I found no published triangle budget for current OSRS player models or equipment.
- I found no Godot-specific writing on which small items low-poly MMO games leave out.

## 7. Web export specifics, Godot 4.3 to 4.7

### Takeaway
The web export runs only [Compat] on WebGL2, single-threaded by default since 4.3, and the docs say that this mode "is not as performant as the multi-threaded export". Shader compiles happen on the render thread at first use, with no ubershader and no shader baker for [Compat], so the client must draw each material and skinned variant one time during a load screen. Two [Compat] faults that matter for this project are not fixed in 4.7: the ANGLE skinning penalty (#124204) and the instance uniform limit (#124336).

### Cited Findings
- [4.7 docs] "Godot 4 can only target WebGL 2.0 (using the Compatibility rendering method)." Forward+ and Mobile do not run on the web. WebGPU is not supported yet. Safari has WebGL 2.0 problems that other browsers do not have. — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- [4.3 and later] Single-threaded web export arrived in 4.3 (PR #85939) and is the default way to export. It "cannot use threads, and is not as performant as the multi-threaded export." Thread support needs the headers `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, or the PWA service worker option. — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html), [Web Export in 4.3](https://godotengine.org/article/progress-report-web-export-in-4-3/)
- [4.3] The 4.3 web build `.wasm` is about 40 MB without compression and about 5 MB with Brotli. — [Web Export in 4.3](https://godotengine.org/article/progress-report-web-export-in-4-3/)
- [4.5] 4.5 turned on WebAssembly SIMD. The release page says web games run "a bit more smoothly" and gives no numbers. "It isn't a silver bullet for poorly optimized games, but it will help nonetheless." — [Godot 4.5 release page](https://godotengine.org/releases/4.5/)
- [4.7] The 4.7 and 4.6 release pages list no change for web export performance, for WebGL, or for [Compat] shader compilation. The 4.7 page says that "the Vulkan Mobile renderer matches or even outperforms our Compatibility renderer in a number of benchmarks", with no figures. — [Godot 4.7 release page](https://godotengine.org/releases/4.7/), [Godot 4.6 release page](https://godotengine.org/releases/4.6/)
- [Compat, 4.4 and later, docs] Ubershaders and pipeline precompilation (new in 4.4) apply "only" to Forward+ and Mobile. For Compatibility: "These versions lack the functionality to effectively implement ubershaders and pipeline precompilation." The fix is the old method: show each material, shader, and particle "for at least one frame" in the view frustum during loading. — [Reducing stutter from shader (pipeline) compilations](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html)
- [Compat, 4.2.1 to 4.7.2, open] Issue #86731 "shader compilation very slow in Compatibility renderer". clayjohn: "In all cases OpenGL limits shader compilation to the rendering thread". He lists Godot-side causes: the cache is saved again on every new specialization, five default modes are more than needed, and the light loop is probably unrolled. A lower maximum light count would help, mainly on the web. — [godotengine/godot issue #86731](https://github.com/godotengine/godot/issues/86731)
- [Compat, 4.7.2 and master, Android native, October 2026] Same issue, one user on a Pixel 5 (Adreno 620) with an empty cache: 15.6 s of total compile time to draw each material one time, with 26 `SceneShaderGLES3` cache entries. A frame with 9 lit materials took about 10 s (about 1.1 s each). The setup step blocked the main thread for 8.0 s on a cold cache against about 0.5 s on a warm cache. The user says that `_initialize_version()` compiles all four scene modes, so one opaque mesh can produce five programs. He marks that last point as an estimate. — [godotengine/godot issue #86731](https://github.com/godotengine/godot/issues/86731)
- [Compat] Same issue: PR #87558 "Reduce shader permutations in the compatibility backend" "would cut initial compile time by 40%", and #87553 "significantly improves the situation". The page does not state the release versions. - [Compat on web, forum, Godot 4.1 to 4.2] Users report that the shader cache settings do not seem to work on the web, and that each new shader stutters on first show. Their fix: show every material or particle for one frame behind a load screen. — [Godot Forum: Handling particle shader compilation lag in Godot 4 web](https://forum.godotengine.org/t/handling-particle-shader-compilation-lag-in-godot-4-web-compatibility-renderer/36170) (read through a search summary)

- [4.6] Issue #115560 reports "memory access out of bounds" errors on release web exports in 4.6.stable, not in 4.5.1. I did not read its present status. — [godotengine/godot issue #115560](https://github.com/godotengine/godot/issues/115560) (read through a search summary)

### Inferences
- Prewarm list for this project, to draw one time off screen or behind the loading veil: the character material, each other material variant (alpha, unshaded, emissive), and one skinned mesh for each vertex format in use. One shared material and one vertex format keep this list to a few entries.
- One shared `StandardMaterial3D` configuration means one scene shader for all characters. A new gear model then never causes a compile hitch, because its material configuration already exists.
- The compile numbers from the Pixel 5 are native Android, not web. A browser adds its own shader translation (ANGLE), so the web can be slower. Light count limits and material features set the size of the shader, so a low maximum light count is worth a test.
- In a single-threaded export, glTF parse, mesh build, texture decode, animation, and render commands all share the main thread. A queue that loads at most one or two models for each frame keeps the hitch small. No source measured the parse cost.
- On the web the two open [Compat] faults both push in one direction: fewer skinned surfaces (merge) and no instance uniforms.

### Gaps
- No source compares frame time of the threaded and the single-threaded export for the same project.
- No source measured `GLTFDocument` parse time or mesh and texture upload time in a web export. I found no issue number for upload hitches in [Compat] on the web.
- I could not confirm which release shipped PR #87553 and PR #87558.
- No official page states the present WebAssembly memory ceiling of a Godot 4.7 web build.
- I did not find out whether the web export keeps a shader cache between sessions. Forum users say that the cache settings do not seem to work on the web.

## 8. Culling and bounds for skinned meshes and bone attachments

### Takeaway
Godot 4 [Compat] computes the bounds of a skinned mesh from an AABB for each bone and the current bone transforms, and it does this again when the skeleton changes. This follows the pose, but it costs CPU time for each skinned mesh. The standard fix for both wrong culling and this cost is `custom_aabb` on each skinned `MeshInstance3D`, or `extra_cull_margin` as the quick form.

### Cited Findings
- [Compat, master source] `mesh_get_aabb` returns `custom_aabb` at once when it is set. With no skeleton it returns the cached mesh AABB. With a skeleton, it transforms the AABB of each used bone by the bone matrix and merges them, then caches the result in `mesh->aabb` with `skeleton_aabb_version`. — [mesh_storage.cpp, GLES3](https://raw.githubusercontent.com/godotengine/godot/master/drivers/gles3/storage/mesh_storage.cpp)
- [4.7 docs] `custom_aabb`: "Overrides the bounding box of this node with a custom one." "This can be used to avoid the expensive AABB recalculation that happens when a skeleton is used with a MeshInstance3D". — [GeometryInstance3D class](https://docs.godotengine.org/en/stable/classes/class_geometryinstance3d.html)
- [4.7 docs] `extra_cull_margin`: "The extra distance added to the GeometryInstance3D's bounding box (AABB) to increase its cull box." — [GeometryInstance3D class](https://docs.godotengine.org/en/stable/classes/class_geometryinstance3d.html)
- [4.7 docs] "To avoid frustum culling, set custom_aabb to a very large AABB that covers your entire game world". To turn off all culling, call `RenderingServer.instance_set_ignore_culling()` on the RID of the instance. — [GeometryInstance3D class](https://docs.godotengine.org/en/stable/classes/class_geometryinstance3d.html)
- [4.x, open] PR #94771 "Fix unintended frustum culling" (open since July 2024, milestone moved to "4.x"). A maintainer (lyuma) wrote: "The AABB on skinned meshes seems wrong until the first update skeleton". clayjohn refused a custom AABB as the fix: "We need to figure why the mesh is getting incorrectly culled". The cause is not found. The report is about the import settings preview. — [godotengine/godot PR #94771](https://github.com/godotengine/godot/pull/94771)
- [Godot 4.6, forum] In an active ragdoll thread, a larger extra cull margin kept the mesh visible but did not stop wrong LOD changes. A reply suggested a custom AABB. — [Godot Forum: Culling issue on active ragdoll](https://forum.godotengine.org/t/culling-issue-on-active-ragdoll/139288) (read through a search summary)
- [4.7 docs] Since 4.6 the default value of `MeshInstance3D.skeleton` is different. The setting `animation/compatibility/default_parent_skeleton_in_mesh_instance_3d` restores the old behavior. — [MeshInstance3D class](https://docs.godotengine.org/en/stable/classes/class_meshinstance3d.html)
- General (PlayCanvas): the engine recalculates the bounds of a skinned mesh every frame, "This operation has a cost for each bone", and a custom AABB avoids it. — [PlayCanvas optimization guidelines](https://developer.playcanvas.com/user-manual/optimization/guidelines/)

### Inferences
- With 100 characters and 11 skinned meshes each, the engine can compute up to 1,100 bone-based AABBs for each frame of animation. A `custom_aabb` on each skinned mesh removes this. One fixed box that covers every pose of a humanoid (for example 2 m wide, 2 m deep, 2.5 m high, with room for a raised weapon) is enough for small characters.
- After a mesh merge there is one AABB for each character, and one `custom_aabb` covers body and gear.
- The cache of the skinned AABB lives on the mesh resource and its key is the skeleton version. Many characters that share one mesh resource with different skeletons can thus defeat the cache or read a box from another character. This is a reading of a source summary, not a confirmed fault. A `custom_aabb` avoids the question.
- A rigid attachment on a `BoneAttachment3D` has a normal AABB from its own mesh, and the box moves with the node. It needs no special fix. A weapon that swings far outside the body box only matters when the body mesh carries the weapon (after a merge), and then the custom box must include the swing.
- A newly merged or newly attached skinned mesh can have wrong bounds until the first skeleton update (lyuma's comment). A forced pose update after the attach, or a `custom_aabb`, avoids one frame of wrong culling.

### Gaps
- I found no godotengine/godot issue that documents skinned meshes that vanish at screen edges in gameplay in 4.x. Three searches of the issue tracker returned nothing on topic. The common advice comes from forum posts and from low-quality blog pages.
- One blog page claims that `extra_cull_margin` works only in Forward+. The official class page gives no such limit. I did not test it.
- No source gives the measured CPU cost of the bone-based AABB update in Godot 4.

## 9. Measured reports from Godot 4 developers

### Takeaway
There are few measured numbers, and none of them is a count of skinned characters at a stated frame rate in a browser. The usable data points say that 50 to 100 animated characters are a safe range on weak desktop hardware in Godot 4.2 to 4.4, that about 300 are possible with culling of animation, and that ANGLE cuts the frame rate of a 50-character scene by a factor of 5.6 on 4.7-era code.

### Cited Findings
- [4.7.x master, Compat, desktop] 50 animated characters (platformer demo, changed), Windows 11, Ryzen 5 9600X, RTX 4080: 560 FPS on native GL, 100 FPS on ANGLE, 220 FPS on ANGLE with PR #124204. — [godotengine/godot PR #124204](https://github.com/godotengine/godot/pull/124204)
- [4.7.2 stable, Compat, desktop, unreviewed report] 14 skinned bodies, 253 draws, 144k primitives, GTX 780, i7-4770K, 1360x768: 1.63 ms render CPU on native GL against 9.9 to 10.2 ms on ANGLE D3D11. — [godotengine/godot PR #124157](https://github.com/godotengine/godot/pull/124157)
- [Godot 4.2, renderer not stated, desktop] One developer: 36 FPS with almost 300 units on a Ryzen 5 2400G with integrated graphics. Units used `AnimationPlayer` only, with animation off for far and off-screen units, no physics bodies, and server calls for ground raycasts. The developer thinks that the load is more CPU than GPU and estimates that 50 to 100 units are safe. "you can get over 50 animated characters on screen at the same time, it depends on the pc." — [Godot Forum: Performance of crowds of animated rigged characters in 3D](https://forum.godotengine.org/t/performance-of-crowds-of-animated-rigged-characters-in-3d/130409)
- [Godot 4.4-dev, Forward+, desktop] One game: about 100 AI characters at 60 FPS with animation on, 3 to 4 times as many with animation off, on an Intel i3-10105F. The reporter says that fewer skeletal mesh surfaces for each frame "heavily helps". — [godotengine/godot issue #101494](https://github.com/godotengine/godot/issues/101494)
- [Godot 4.x against other engines, 2024, no detail] A maintainer (fire) cites an external comparison with 500 skeleton meshes: Flax 132 FPS, Godot 23 FPS, Unreal 28 FPS. The page gives no hardware and no scene data. — [godotengine/godot issue #101494](https://github.com/godotengine/godot/issues/101494)
- [Godot 3.6 to 4.4-dev7, M2 MacBook Pro] 2,400 instances with `AnimationPlayer` and `AnimationTree`: 6.2 ms in 3.6, 11.75 ms in 4.2.2, 13.5 ms in 4.3, 11.0 ms in 4.4-dev7. — [godotengine/godot issue #101494](https://github.com/godotengine/godot/issues/101494)
- [Godot 4.3-dev, Forward+] 1,024 characters with `AnimationPlayer` and `AnimationTree` on a GTX 1080 and a Ryzen 5 1600: process time 25 to 30 ms against 16 ms. — [godotengine/godot issue #92693](https://github.com/godotengine/godot/issues/92693)
- [Godot 4.5.1, add-on, vertex animation textures] About 50,000 instances at a steady 100 FPS with models under 500 vertices on an RTX 2070 SUPER. — [shadecoredev/AnimatedMultimeshInstance3D README](https://raw.githubusercontent.com/shadecoredev/AnimatedMultimeshInstance3D/main/README.md)
- [Godot 4.5.1, web against native, not skinned] An RTS port poses rigid unit parts into `MultiMesh` buffers from C++. Simulation for 2,000 units: 15.0 ms mean in the browser JavaScript version against 1.21 ms in Godot C++. The render numbers used software GPUs (SwiftShader and lavapipe) and do not transfer. — [slamcoderpt/ageofvoxel PR #3](https://github.com/slamcoderpt/ageofvoxel/pull/3)
- [Godot 4, physics, not rendering] Issue #93184: 384 moving `CharacterBody3D` nodes went from 90 FPS to 320 FPS with Jolt and other fixes, with visuals mostly off. This shows that physics bodies can be the limit before rendering. — [godotengine/godot issue #93184](https://github.com/godotengine/godot/issues/93184) (read through a search summary)

### Inferences
- For 20 to 100 characters, desktop native GL has a large margin on mid-range hardware, on condition that animation is a bare `AnimationPlayer` and that the draw count stays in the low thousands.
- The web target has the smallest margin. It has the ANGLE penalty on Windows, single-threaded WebAssembly for animation, and WebGL call overhead for each draw. A frame budget for 100 characters on the web must come from a test scene of the project.
- A useful stress test for this project: 100 characters, each with 1 body and 10 gear meshes, in four builds (separate meshes or merged, native GL or web). Record the frame time, the draw calls, and the time of `advance()` calls. No published number replaces this test.

### Gaps
- I found no GodotCon talk and no official blog post with measured numbers for skinned character crowds in Godot 4.
- I found no report of the form "N skinned characters at 60 FPS in browser X on hardware Y" for Godot 4.
- The fire comparison (500 skeleton meshes) has no primary source in the page that I read.

## 10. Measurement: tools and monitors, and what works in a web export

### Takeaway
The `Performance` singleton and `Viewport.get_render_info` give the draw calls, primitives, and objects of each frame from script, in every renderer, so a small on-screen readout works in a web export too. The pipeline compilation monitors only matter for Forward+ and Mobile. For the web, the sure tools are the in-game readout and the profiler of the browser. I could not confirm from official 4.7 docs that the editor debugger attaches to a web export.

### Cited Findings
- [4.7 docs] `Performance.RENDER_TOTAL_OBJECTS_IN_FRAME`, `RENDER_TOTAL_PRIMITIVES_IN_FRAME`, and `RENDER_TOTAL_DRAW_CALLS_IN_FRAME` report the last rendered frame. Culled objects do not count. `RENDER_VIDEO_MEM_USED`, `RENDER_TEXTURE_MEM_USED`, and `RENDER_BUFFER_MEM_USED` report bytes. The page states no renderer limit for these. — [Performance class](https://docs.godotengine.org/en/stable/classes/class_performance.html)
- [4.7 docs] `TIME_FPS` updates one time each second. `TIME_PROCESS` is the time for one frame in seconds. `MEMORY_STATIC`, `MEMORY_STATIC_MAX`, and `OBJECT_ORPHAN_NODE_COUNT` return 0 in a release export. — [Performance class](https://docs.godotengine.org/en/stable/classes/class_performance.html)
- [4.7 docs] `Performance.add_custom_monitor(id, callable, arguments, type)` adds a custom value to the Monitor tab of the debugger, for example `"Game/NumberOfNPCs"`. — [Performance class](https://docs.godotengine.org/en/stable/classes/class_performance.html)
- [4.7 docs] `Viewport.get_render_info(type, info)` splits the counts by pass: `RENDER_INFO_TYPE_VISIBLE` ("Visible render pass (excluding shadows)"), `RENDER_INFO_TYPE_SHADOW`, and `RENDER_INFO_TYPE_CANVAS`. The values are objects, primitives, and draw calls in the frame. — [Viewport class](https://docs.godotengine.org/en/stable/classes/class_viewport.html)
- [4.7 docs] The pipeline compilation monitors (`PIPELINE_COMPILATIONS_CANVAS`, `_MESH`, `_SURFACE`, `_DRAW`, `_SPECIALIZATION`) belong to the pipeline system of Forward+ and Mobile. The pipeline page "only applies to the Forward+ and Mobile renderers, not Compatibility." — [Performance class](https://docs.godotengine.org/en/stable/classes/class_performance.html), [Reducing stutter from shader (pipeline) compilations](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html)
- [4.7 docs] Viewport debug draw has an overdraw mode and a wireframe mode. For wireframe in the Compatibility renderer, "RenderingServer.set_debug_generate_wireframes() must be called before loading any meshes". — [Viewport class](https://docs.godotengine.org/en/stable/classes/class_viewport.html)
- [4.7 docs] Fill rate test: turn off V-Sync and compare the FPS in a large window and in a very small window. — [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)
- [4.6 and 4.7] 4.6 added support for C++ tracing profilers (Tracy, Perfetto, Instruments) and ObjectDB snapshots. 4.7 made Perfetto the default tracing tool for Android editor and template builds. — [Godot 4.6 release page](https://godotengine.org/releases/4.6/), [Godot 4.7 release page](https://godotengine.org/releases/4.7/)
- [Godot 4.3-dev, method] A user measured the animation cost for each instance with Tracy (`_process_animation`, `AnimationMixer::_blend_process`). This is the method that gave the 40 microsecond figure. — [godotengine/godot issue #92693](https://github.com/godotengine/godot/issues/92693)
- [4.4 docs, web] In a web export, the developer console of the browser (F12) shows JavaScript, engine, and WebGL errors. — [Exporting for the Web, 4.4](https://docs.godotengine.org/en/4.4/tutorials/export/exporting_for_web.html) (read through a search summary)
- [Godot 4.0 development, old] A Godot blog post from the 4.0 development period says that remote debugging of HTML5 exports supports all debugger features except breakpoints. The post predates 4.0 and I did not confirm it for 4.7. — [HTML5 export profiling for Godot 4.0](https://godotengine.org/article/html5-export-profiling/) (read through a search summary)

### Inferences
- A debug overlay that prints `Performance.get_monitor()` values and `get_render_info()` counts works in every export, the web included, because it is plain script. It is the most reliable tool for the web target.
- The draw call monitor counts scene draws. It probably does not count the transform feedback passes of skinning. The CPU time of those passes shows only in a frame time measurement or in a native profiler. I did not confirm this in the source.
- To split CPU cost on the web: measure the frame time with animation stopped (`active = false`), then with frozen skeletons, then with all characters hidden. The three differences give animation cost, skinning cost, and draw cost. PR #124157 used the same method on desktop.
- Run the desktop build with the `opengl3_angle` driver to see the ANGLE cost with native tools. This is the driver name that PR #124157 used. It is the closest desktop stand-in for a Windows browser.
- The browser performance profiler shows WebAssembly time and WebGL call time in one view. It is the tool for upload and compile hitches on the web.

### Gaps
- I did not read the official pages for the script profiler, the visual profiler, and `RenderingServer.get_rendering_info` in this research. I could not confirm whether the visual profiler reports GPU time in the Compatibility renderer, or on the web.
- No official 4.7 page that I read confirms that the editor debugger, the profiler, or the monitors attach to a running web export.
- I did not confirm `RenderingServer.viewport_set_measure_render_time` and its getter functions against the 4.7 class reference.
